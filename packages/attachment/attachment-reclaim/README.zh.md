# @deepseek-ai/dsh-attachment-reclaim

[English](README.md) | 中文

<a id="summary"></a>
## 概述

本包回答“是否还有会话引用某个内容寻址的附件对象”，并在没有任何会话引用它时把该对象从磁盘移除。附件存储按内容寻址：上传相同字节的两个会话共用同一个对象，因此删除其中一个会话绝不能让另一个会话失去它的图片。引用只从已提交的会话事件读取，而不是另建一套需要同步维护的账目；回收在后台运行，并同时使用完整性闸门、本进程认领记录与对象存在时间闸门，所以失败只会多占磁盘，绝不会让会话失去它的字节。

<a id="use-this-package"></a>
## 使用本包

在任何会删除会话的组合中，把本插件与附件后端一起挂载。它不写任何会话事件，也不添加提示词或工具 schema。

### 何时选择

凡是“被删除的会话会把字节遗留在磁盘上”的场景都选择它：账本是唯一知道哪个会话引用了哪个对象的组件。从不删除会话的组合可以省略它，而省略不会改变其他行为——除了自身的扫描之外，没有谁依赖账本。愿意用磁盘换取更快回收的部署可以调低 `minAgeMs`；宁可留下孤儿也不愿承担误删风险的部署则调高它。

### 最小配置

```yaml
- id: attachment-reclaim
  name: '@deepseek-ai/dsh-attachment-reclaim'
  config:
    reclaimIntervalMs: 60000
    minAgeMs: 600000
    batchSize: 50
    concurrency: 4
```

`minAgeMs` 是一个对象在被扫描移除前必须达到的最短存在时间，也是本进程为刚提交对象所持认领记录的有效期。`reclaimIntervalMs` 决定扫描频率，`batchSize` 限定单趟处理的排队对象数量，`concurrency` 限定单趟保持在途的后端调用数。

### 什么会变得持久

采用 `per-record` 布局的 `attachment_refs` 域：一条 `refs` 记录列出引用某个对象的会话；一条 `reclaim` 记录等待移除的对象，携带其入队时间、重试次数与最近一次失败原因。两张表都以 64 位十六进制摘要本身作为键，因为逐条记录布局要求键可用于路径。全局槽位保存 `builtAt`，即这些记录最近一次从全部已存会话日志重建完成的标记。

### 可观察行为与失败

引用只在会话事件提交时登记，因此被拒绝的消息或中途放弃的上传不会留下记录。当工作区注册表宣布 `workspace/session-deleted` 时，本包把该会话从每一条提到它的记录中移除，并为失去最后一个持有者的对象排队。一次扫描只有在四个条件同时成立时才会移除对象：账本可信、没有任何 `refs` 记录仍有持有者、本进程刚提交的对象没有仍在等待引用落地、并且后端确认对象已经足够旧且未被占用。移除失败会保留排队条目与其记录的原因，留待下一趟。

某次重建读不出某份已存日志时，账本保持不可信、扫描空转，因为缺失的引用可能删掉某个会话仍在展示的图片。下一次完整重建会恢复可信，所以短暂的存储故障只是推迟回收，而不是带来丢失风险。

<a id="understand-the-implementation"></a>
## 理解实现

<details>
<summary>实现细节——点击展开</summary>

会话日志是“谁引用了什么”的唯一权威，因此账本是它的投影。引用在事件提交时进入，在日志被宣布移除时离开；当持久记录缺失、过期或不可信时，整个投影可以由日志重建。移除被推迟、并在真正删除的那一刻再次核对，理由相同：多留一个对象只是浪费字节，误删一个对象却是丢失对话记录。

### 设计理念

三条规则决定全部情形。第一，只有已提交事件会创建引用，这让从未落到日志的认领不会永久占住对象。第二，对象只有在扫描重新读取账本之后才会移除，因此其间再次引用它的会话仍保有自己的图片。第三，账本只有在完整时才可用于删除：缺失或只重建了一半的 `refs` 表证明不了任何事，而完整性只能靠读取全部已存日志确立，这就是 `builtAt` 充当扫描闸门、而不只是记录“曾经跑过一趟”的原因。

### 源码地图

| 文件 | 职责 |
| --- | --- |
| `src/index.ts` | `ctx.attachmentReferences` 服务：`Config`、引用登记、删除时摘除、重建与回收扫描。 |
| `src/spec.ts` | `attachment_refs` 域声明及其记录 schema。 |
| `src/refs.ts` | 结构遍历，从一条已提交事件中收集全部内容地址。 |

</details>

<a id="model-experience"></a>
## 模型体验

### 某个会话被删除

#### 模型看到什么

存活的会话不发生任何变化。被删除的会话不会再进入后续任何请求，而它对话中被其他会话引用的部分会报告为来源不可用，而不是日志损坏。它仍引用的图片可以继续解析，因为只有当 `workspace/session-deleted` 之后没有任何日志仍指名该对象时，它才会被回收。

#### Token 影响

不增不减 token：账本不写任何会话事件，因此对话记录不会变长，也不会向提示词注入任何内容。

#### KV Cache 影响

无。回收运行在请求路径之外，无法改写提示词内容。

## 已知限制与延期工作

<a id="known-limitations-and-deferred-work"></a>

以下限制界定了回收停止的位置，它们是本包当前的约束，而不是待办清单。

- **回收以一次删除为范围** —— 从未被任何日志引用的对象不会被清扫，因为发现它需要枚举后端已存的全部摘要，而 `ctx.attachments` 不提供该能力。
- **已存字节但未落事件的对象只在本进程受保护** —— 另一个进程提交了字节却在事件落地前消亡，会留下无人引用的对象；对象存在时间窗口限制了这种暴露，而非消除它。
- **存储故障会推迟回收** —— 账本不可信期间扫描空转，因此磁盘占用可能比 `minAgeMs` 所承诺的更久。

<a id="dev-note"></a>
### 开发备注

<details>
<summary>面向维护者的工作背景——点击展开</summary>

排队记录保留重试次数与最近一次失败原因，因此一个卡住的对象只靠介质本身就能诊断。单个对象的失败不会让扫描抛出异常，而是留待下一趟重试，这就是扫描返回计数而不是被拒绝 Promise 的原因。

</details>
