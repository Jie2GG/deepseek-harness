# Agent Note: 模型设置里的提供商超时字段

状态：implemented

[English](2026-11-10-models-provider-timeout-field.md) | 中文

## 问题

以手动声明的 `llm-pi-ai` 路由挂载的网关在预填充长上下文时，可以把请求保持打开十分钟以上，因为预填充结束之前没有任何 token 上线。这条等待路径上有两个截止时间，每层一个：适配器的流空闲看门狗（`streamIdleTimeoutMs`，默认 300 秒）与 SDK 层使用的提供方客户端（`timeoutMs`，pi-ai 封装的 OpenAI 与 Anthropic 客户端默认十分钟）。首字晚于两者中较短者的请求会以可重试的 `TIMEOUT` 结束，而每次重试都要重新预填充。Models 设置页既不展示也不写入这两个键，所以为慢网关放宽等待只能手改 `cordis.patch.yml`，而只放宽其中一个键仍会在另一个键处结束请求。

## 决策

- 自定义模型 API 的创建卡片在端点下方提供一个可选的**模型超时时间（秒）**，手动声明路由的编辑卡片也在收起的「自定义设置」区里、与显示名称和 API 协议并排提供同一个字段。填了值就把同一个整数毫秒同时写入 `providers.<route>.streamIdleTimeoutMs` 与 `providers.<route>.timeoutMs`；留空则两个键都不写。
- 一个字段同时管两个键，因为它们从两层约束同一次等待。只放宽其中一个键的 profile 仍会在另一个键处结束请求，而这正是该字段要消除的故障。
- 输入单位是秒，且不接受单位后缀。落盘仍是毫秒，因为两个 profile 键、适配器默认值与 SDK 选项都以毫秒计；输入用秒，因为运维要选的值都是分钟量级，而最小的有用毫秒数已经要有四位数。
- 编辑卡片的占位符是这个字段清空后要回到的那一层——组合条目里已存的值，否则是适配器自身 schema 会解析出的默认值——清空字段会把两个键一并 unset。只带其中一个键的 profile 按 `streamIdleTimeoutMs`、其次 `timeoutMs` 回显，并且只在字段被改动时才重写，所以手写的单键 profile 在一次无关编辑之后仍保持原样。
- 走 pi-ai 已安装目录的路由与 `llm-deepseek` 卡片都不显示该字段。已发行路由的能力来自它的目录条目，而占据整节的 `llm-deepseek` profile 是组合事实，不是本页创建的路由。

## 考虑过的替代方案

**只写 `streamIdleTimeoutMs`。** 提供方客户端仍保留自己的请求截止，所以运维即便填了更长的空闲预算，还是会收到 SDK 抛出的 `TIMEOUT`，并为此再付一次预填充。

**两个字段各管一个键。** 直接写明映射关系，但要用户为同一次等待保持两个数字一致；两者不一致就悄悄把较短的那个约束放回来，而那正是待修的故障。

**不加字段，直接抬高随发行版交付的默认值。** 让每条路由的停顿检测一起变钝，僵死的网关要等满新的上限才报错；默认值变化对外可感知，却只为部分网关的需要服务。

**字段按毫秒填写。** 与落盘形式一致，但有用的值都是六位数，一个写错的数字就把截止时间挪走一个数量级。

**秒再加单位后缀（`30m`、`1h`、`1800s`）。** 读起来好，但要区分 `m` 与 `ms`、还要容忍空格与小数的解析器，比一个标明单位的字段带来更多表面复杂度。

## 后果

经由本页创建或编辑的路由现在带有显式的毫秒值，它们会盖住适配器默认值，直到该字段被清空；预填充慢的路由的预算从此在浏览器里设定，而不再依赖 `cordis.patch.yml`。重试策略、请求图片预算与 profile `headers` 仍只能配置，且该字段不写任何会话事件：这两个 profile 键就是它的持久记录。

## 测试

`packages/client/ui-settings-models/tests/timeout-value.client.spec.ts` 覆盖解析与回显，包括空白、带单位后缀、零、负数、亚毫秒与超上限输入，并把每个被接受的值原样读回。`packages/client/ui-settings-models/tests/provider-form.client.spec.tsx` 断言创建卡片由一次输入写入两个键、字段留空时一个都不写、不可读的时长会禁用创建并点名该字段，以及编辑卡片把已存的那对值按秒回显、改动时重写两个键、清空时 unset 两个键，并且不改动手写的单键 profile。Web 流程 `apps/web/tests/models-settings.e2e.ts` 把该字段写入真实的 settings 文档，并把已声明路由的卡片与可访问性基线比对。
