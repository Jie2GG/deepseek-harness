# Agent 笔记：以删除会话日志作为提交点，且只从已提交事件推导附件回收

Status: implemented

[English](2026-11-06-session-delete-commit-point-and-committed-attachment-reclaim.md) | 中文

## 问题

删除会话不可逆，而三个性质彼此冲突。会话列表、搜索与派生读取全部由已存日志投影而来，所以只要日志还在，任何记账记录都改变不了它可见这一事实。附件对象按内容寻址且被共享，因此移除最后一个引用它的会话，其字节可能已无用，也可能仍被他人使用。持久写入还可能被中断：进程可能在写下意图之后、完成该意图所指的移除之前退出，而 Windows 会拒绝删除另一个句柄仍占用的文件。

为这些步骤选择顺序是代码表达不出来的决定。顺序错了，要么展示一个已不存在的会话，要么藏起一个字节仍在磁盘上的会话，要么删掉另一个会话即将引用的图片。

## 决定

### 日志移除就是提交点，旁边放着持久意图

`WorkspaceRegistry.deleteSession` 先记录 `pendingSessionDeletions`，再调用 `ctx.sessionPersistence.delete`，最后才把该会话从工作区记录以及归档、置顶集合中删除。因此移除那一刻就是它在所有读取面上消失的时刻，因为这些读取面都由日志投影。

启动时在常规引导之后为每个待删 id 重跑移除，于是中断会在下一次启动收敛，而不需要修复动作：日志再被删一次——不存在不算错误——记账随即去掉该 id。仍然删不掉的（另一个进程持有句柄）保留意图并保持会话可见，这正是事实：它的日志还在。

`workspace` 域沿用 version 2，新字段靠 zod 默认值承接，而不是提升版本。`archivedSessionIds` 与 `pinnedSessionIds` 当初同样引入：写于该字段之前的状态读作空集合，且没有任何已存形状发生搬迁，因此欠不上一个后继代次。

### 引用在事件提交时才存在

`attachment_refs` 记录哪个会话引用哪个对象，且只从已提交的会话事件学习引用。账本是日志的投影，绝不是第二权威：读不出某份已存日志的重建不会写下 `builtAt`，而不可信的账本什么都不回收。收敛依靠重建完成。

### 三重闸门缺一不可

一趟扫描只在同时满足三个条件时才移除排队对象：账本里没有持有者；本进程没有为刚提交、尚未被引用的对象持有条目；后端确认该对象已足够旧且未被占用。每一道闸门都堵上其余闸门留下的窗口：持有者检查覆盖“对象排队之后又有会话引用它”；本进程条目覆盖“字节已发布、指名它的事件尚未提交”这段时间，而这从一个由日志推导的账本里根本看不见；后端时间闸门跨进程、并在崩溃后条目无法存活时覆盖同一段时间。

条目刻意只放进程内存，不做持久表。回收仍以一次删除所释放的范围为限：从未被任何日志指名的对象不会被清扫，因为发现它需要枚举后端已存的全部摘要，而 `ctx.attachments` 目前不提供该能力。

### 删除靠宣布，不靠调用

注册表在自己的持久写入之后发出 `workspace/session-deleted`，每个持有该会话派生记录的所有者据此退役自己的副本：引用账本摘除持有者，投影缓存删掉检查点行。

## 已考虑的替代方案

- **先清记账，再删文件** —— 列表与搜索会在下一次启动时把这个会话复活，因为历史引导流程会重新登记扫描仍能找到的一切日志。那一行会先消失再回来，而字节会比“它已不存在”的记录活得更久。
- **带自身保留策略的回收站目录** —— 为同一份字节引入第二种生命周期、一份隐藏配额，以及一条“数据仍在却隐藏行”的列表规则，换来的却是从未向用户承诺过的撤销。风险改由确认框与“正在运行的会话被拒绝删除”承担。
- **在对象保存时就登记引用** —— 会把对象钉给一条被拒绝、从未发出、或随进程退出丢失的消息，而且无人解锁：日志才是记录会话究竟包含什么的地方。
- **删除时按摘要扫描全部已存日志** —— 结论正确且无需新状态，但每次删除都要重读整个 Home，而这个答案账本本可增量维护。
- **把 SQLite 搜索索引当作权威** —— 索引中的附件文本只带缩短后的摘要，因此漏检与“确实没有引用”无法区分，而缺失的引用会删掉某个会话仍在展示的图片。
- **做一张持久的在途认领表** —— 需要自己的过期规则，必须由后来的进程在崩溃后清理，还可能比它本想保护的那次上传活得更久，从而重新引入它想避免的泄漏。时间闸门已经约束了跨进程情形，而真正删除前的重读才是让在途引用安全的手段。
- **把 `workspace` 域提升到 version 3** —— 会为形状从未改变的数据暗示一个后继代次和一次迁移，与相邻迁移规则相悖：只有无法原样解析的已存形状才配得上新版本。
- **由注册表直接调用账本与缓存** —— 只为传递一条已声明事件本就承载的通知而颠倒依赖方向，还会让删除动作取决于可选插件是否存在。

## 后果

删除要么移除日志，要么说明为什么没移除：不存在“会话被隐藏而字节仍在”的状态，也不需要为写在两次写入之间的崩溃准备修复步骤。代价是被活跃写入器阻塞的会话会带着待删意图保持可见，直到那个句柄关闭，因此界面是重试，而不是收到一次静默成功。

附件只在一次完整重建之后才回收，所以全新安装在首次成功扫描之前会保留所有对象；存储故障只会推迟回收，不会带来丢失风险。共享对象按构造在每一次单会话删除中存活：决定权在持有者集合，而不在发起删除的调用方。

回收不会处理从未被任何日志指名的对象，因此在本包出现之前就已积累孤儿的 Home 会把它们留下，直到 `ctx.attachments` 能够枚举已存摘要为止。
